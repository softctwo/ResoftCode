v0.1.2 ships the Resoft CodingAgent CLI on top of the freshly
rebased upstream kilo-org v7.3.31 baseline. The internal
diff is bookkeeping only — no Resoft-owned behavior change
between v0.1.1 and v0.1.2 — but the build artifact needs to be
re-published so that anyone running `npm install -g
@chinaresoft/resoftcode@latest` gets the post-rebase tarball
rather than the v0.1.1 one (which was built from a 232-commit-
behind source).

What changed since v0.1.1:

  - **Upstream sync**: pulled in 232 commits from
    kilo-org/main, including release 7.3.30 and 7.3.31.
  - **New upstream deps surfaced** in the v0.1.1 tarball's
    lockfile but never published (e.g. `@kilocode/plugin-atomic-
    chat`): these are now reachable from a clean install on the
    v0.1.2 tarball.
  - **`bun.lock`**: regenerated to match the v7.3.31 dep graph;
    `bun install` from the v0.1.1 tarball no longer needs to
    re-resolve 80+ workspace closures.
  - **`postinstall.mjs`**: cleanup of a leftover conflict marker
    and a duplicate `fs.chmodSync` that the rebase had silently
    left in place.
  - **`package.json`**: `private: false` restored to match
    upstream; `script/build.ts` and `script/publish.ts` read
    this field when writing the dist `package.json` and the
    typecheck on the v0.1.1 branch had been failing on
    `Property 'private' does not exist`.

The Resoft-owned work shipped in v0.1.1 (deepseek 1M context,
mock SQL MCP server, 9-agent starter, `--context` / `--output`
overrides, VS Code extension bridge, OEM marker on a sibling
`.resoft-version` file) is unchanged in v0.1.2.

Upgrade:

```sh
npm update -g @chinaresoft/resoftcode
resoftcode --version  # 0.1.2
```

The internal rebase was committed in f16e0339ea on this branch;
the published tarball will be rebuilt from the resulting source
tree.

# 监管报送 Mapping 分析 Skill

## 概述

本 Skill 用于金融行业监管报送场景中的**源系统→监管制度字段映射分析**。
输入行内源系统的数据字典、数据库设计文档及辅助业务文档，
对照监管报送目标制度，输出逐字段的映射关系初稿和差异分析报告，
支撑业务分析师与客户访谈验证。

## 适用场景

- EAST（银保监会监管数据标准化规范）报送
- 1104 非现场监管报表
- 反洗钱（AML）大额/可疑交易报送
- 征信（个人/企业）报送
- 大集中、金融基础数据、利率报备等其他监管报送
- 数据仓库/数据湖的监管集市 mapping 设计

## 工作流程

### 第一阶段：资料收集与理解

1. **读取源系统数据字典**
   - 识别和解析数据字典文件（Excel/Word/PDF）
   - 提取：表名、字段名、字段类型、字段长度、字段含义、是否必填、主键/外键、枚举值说明
   - 梳理表间关联关系（外键、业务关联）

2. **读取数据库设计文档**
   - 解析数据库设计说明书、ER 图描述
   - 提取：系统架构、数据流转、核心实体关系
   - 标注各表所属业务模块（核心系统、信贷系统、理财系统等）

3. **读取辅助业务文档**
   - 业务需求说明书、接口规范、业务流程图
   - 提取业务流程与数据产生的对应关系
   - 识别数据质量约束和业务规则

### 第二阶段：监管制度解读

4. **读取监管报送制度文档**
   - 识别报送制度的结构（报送范围、报送频率、数据表清单）
   - 提取每个报送字段的：字段编码、字段名称、数据类型、长度、填报说明、校验规则、枚举值约束
   - 标注各字段的必填/条件必填属性

5. **制度要点提炼**
   - 提取关键业务规则和校验逻辑
   - 识别跨表一致性要求
   - 标注容易出错的字段

### 第三阶段：Mapping 映射分析

6. **逐字段映射分析**
   对每个监管字段逐一分析：
   - 源系统是否存在对应字段（直接映射/间接映射/计算得来/源系统缺失）
   - 字段类型和长度是否匹配
   - 数据格式是否需要转换（编码映射、格式转换、单位转换）
   - 业务逻辑是否需要加工（聚合、拆分、关联多表）

7. **映射分类标注**
   - ✅ **可直接映射**：源字段与监管字段一对一直接对应
   - 🔄 **需转换映射**：源字段存在但需要格式/编码/逻辑转换
   - 🧩 **需加工计算**：需要多个源字段组合或计算才能得出
   - ❌ **源端缺失**：制度要求但源系统中无对应数据
   - ⚠️ **待确认**：映射关系需要业务专家确认

8. **差异分析**
   - 字段类型不一致（如源端 varchar 但要求 date）
   - 字段长度不足（源端 50 位但要求 100 位）
   - 枚举值不匹配（源端和制度编码体系不同）
   - 必填字段源端缺失

### 第四阶段：输出交付

9. **生成 Mapping 表**
   输出标准化的 Excel mapping 表，包含以下列：

   | 列名 | 说明 |
   |------|------|
   | 报送表名 | 监管报送的目标表/报文名称 |
   | 监管字段编码 | 监管制度中的字段编号 |
   | 监管字段名称 | 监管制度中的字段中文名 |
   | 监管字段类型 | 监管要求的字段类型 |
   | 监管字段长度 | 监管要求的字段长度 |
   | 是否必填 | 监管要求的必填属性 |
   | 填报说明 | 监管制度的填报说明 |
   | 映射类型 | 直接映射/需转换/需加工/源端缺失/待确认 |
   | 源系统名称 | 数据来源的源系统 |
   | 源表名 | 源系统中的表名 |
   | 源字段名 | 源系统中的字段名 |
   | 源字段类型 | 源系统的字段类型 |
   | 源字段长度 | 源系统的字段长度 |
   | 转换/加工逻辑 | 数据转换或计算逻辑说明 |
   | 差异说明 | 类型、长度、格式不一致等差异 |
   | 确认状态 | 待确认/已确认/不适用 |
   | 备注 | 其他需要说明的事项 |

10. **生成分析报告**
    输出 Word 分析报告，包含：
    - 分析概述（范围、方法、依据）
    - 源系统概况（涉及系统、表数量）
    - 映射统计（各类映射类型的数量和占比）
    - 差异清单（高风险差异逐条说明）
    - 建议与风险提示
    - 待确认事项清单（供客户访谈使用）

### 第五阶段：迭代支持

11. **支持客户访谈**
    - 将 mapping 初稿中的「待确认」项和差异项整理成访谈问题清单
    - 标注优先级：高（影响报送合规）/ 中（影响数据质量）/ 低（可后续优化）
    - 支持按问题类型筛选（数据缺失、口径差异、格式不匹配等）

12. **根据访谈结果修正**
    - 更新 mapping 表的确认状态和处理方案
    - 修正转换/加工逻辑
    - 重新生成差异分析

## 使用方式

### 基础用法

```
请分析 [监管制度名称] 报送的 mapping 关系，
源系统数据字典在 [文件路径]，
数据库设计文档在 [文件路径]，
报送制度文档在 [文件路径]。
```

### 示例

```
请分析 EAST 5.0 报送的源系统 mapping 关系，
源系统数据字典：./docs/源系统数据字典.xlsx
数据库设计文档：./docs/核心系统数据库设计.docx
辅助文档：./docs/信贷业务流程说明.docx
报送制度：./docs/EAST5.0报送规范.xlsx
```

## 最佳实践

1. **分批处理**：大型报送制度（如 EAST 含数百个字段）建议按数据表/主题域分批分析
2. **优先高风险**：先处理必填字段和核心业务字段的映射
3. **保留分析痕迹**：所有推断和假设都标注为「待确认」，不要代替业务专家做决策
4. **版本管理**：初稿和每次迭代修正后的版本单独保存，便于追踪变更
5. **结合客户上下文**：了解银行使用的具体核心系统厂商（如长亮、中联、宇信等），可提高映射准确性

## 支持的文档格式

该 Skill 可处理以下格式的输入文档：
- Excel (.xlsx/.xls)：数据字典、报送制度规范
- Word (.docx)：数据库设计说明书、业务需求文档
- PDF (.pdf)：监管制度原文、接口规范
- Markdown (.md)：技术方案、接口说明
- 纯文本 (.txt/.csv)：数据字典导出

## 注意事项

- 该 Skill 生成的是**分析初稿**，必须经过业务分析师和客户访谈验证后才能作为最终方案
- 不同报送制度的字段命名和编码体系差异很大，分析时要以制度原文为准
- 同一字段可能在多个源系统中存在（如客户名称在核心系统、信贷系统、ECIF 中都有），需要标注主要来源和备选来源
- 监管制度会定期升级（如 EAST 4.0→5.0），需要关注版本差异

# EAST 报送分析指南

## EAST 监管数据标准化规范概述

EAST（Examination and Analysis System Technology）是银保监会推行的监管数据标准化规范，
要求银行等金融机构按照统一的数据标准报送业务数据。

## EAST 版本演进

| 版本 | 发布年份 | 主要变化 |
|------|---------|---------|
| EAST 1.0 | 2012 | 初始版本，覆盖基础业务 |
| EAST 2.0 | 2014 | 扩展表结构，增加字段 |
| EAST 3.0 | 2016 | 大幅扩展，增加理财、同业等 |
| EAST 4.0 | 2019 | 重构部分表，增强数据质量要求 |
| EAST 5.0 | 2022 | 全面升级，新增表、字段大幅增加 |

## EAST 数据结构特点

EAST 规范通常包含以下类型的报送表：

### 公共信息表
- 机构信息、员工信息等基础主数据

### 客户信息表
- 对公客户、个人客户基本信息
- 关联方信息、实际控制人

### 账户信息表
- 存款账户、贷款账户、信用卡账户
- 账户状态、利率信息

### 交易信息表
- 存款交易、贷款交易、支付交易
- 交易对手信息

### 信贷管理表
- 授信、用信、担保、押品
- 五级分类、减值准备

### 其他
- 理财、同业、债券、衍生品等

## 常见映射难点

### 1. 客户信息
- 客户统一编号（ECIF 号）在各系统可能不一致
- 客户类型划分口径不同
- 实际控制人/受益所有人信息缺失

### 2. 信贷数据
- 授信额度的口径（合同额度 vs 可用额度 vs 已用额度）
- 五级分类的时点和机构范围
- 担保方式的多重分类
- 押品评估价值的时效性

### 3. 交易数据
- 交易对手信息在核心系统中可能不完整
- 资金用途、交易附言的规范性
- 跨行交易的对方行信息

### 4. 会计数据
- 科目体系的差异（旧准则 vs 新准则）
- 总账与分户账的一致性
- 减值准备的计算口径

## 分析检查清单

- [ ] 是否识别了所有涉及的源系统
- [ ] 主键字段的映射是否准确
- [ ] 枚举值/代码表的映射是否完整
- [ ] 日期时间格式是否一致
- [ ] 金额字段的精度和单位是否对齐
- [ ] 必填字段是否都有来源
- [ ] 跨表关联字段是否一致
- [ ] 条件必填字段的条件是否可判断
- [ ] 数据清洗规则是否明确
- [ ] 默认值和空值处理策略是否定义

## 格式要求

- 映射类型列使用条件格式：
  - ✅ 绿色背景
  - 🔄 黄色背景
  - 🧩 橙色背景
  - ❌ 红色背景
  - ⚠️ 灰色背景

- 差异等级列使用条件格式：
  - 高 → 红色字体
  - 中 → 橙色字体
  - 低 → 无特殊格式

- 首行冻结，自动筛选启用
- 字体：微软雅黑，正文 10pt
